> 状態: 基盤実装中。入力モデル・独立した技能計算・購入価格を実装済み。既存計算への接続、画面、キャリア、入出力のv2対応・公開は未実施。

## 1. 目的と完了条件

モジュール由来の技能を、人生段階ごとのルールに従って上限まで付与する。
実生活で発生した対象技能の超過分は、利用者が同じ関連能力値の別技能へ移せるようにする。
移したレベルは無償付与として扱い、その後のカルマ購入を正しく課金する。
再計算、モジュール変更、保存・復元、キャリア移行で付与の重複・消失・復活を起こさない。

この文書は機能要件から実装単位・受入試験まで定義する。原典確認済みの範囲と
アプリとして採用する解釈を区別する。未確認の解釈を「Chummer5a の仕様」と呼ばない。

## 3. 採用するルールと適用表

### 3.1 上限と超過

`policy_version = "rf66-76-v1"` を本設計の判定規約とする。
作成上限は LifeModule の未指定時だけアクティブ7・知識9を使い、他方式は変えない。
`settings.chargen_skill_max` / `chargen_knowledge_skill_max` が明示されていれば優先する。
明示値6を7へ強制変更しない。表示には「標準」「設定による変更」を区別する。

| 付与対象・発生段階 | 上限内 | 超過分 |
| --- | --- | --- |
| アクティブ、Nationality / Formative / Teen / Further Education | 無償加算 | p.66 に従い切り捨て。警告と履歴を残し、モジュール自体は許可 |
| アクティブ、Real Life、元技能にグループ所属なし | 無償加算 | 移し替えプールを生成 |
| アクティブ、Real Life、元技能にグループ所属あり | 無償加算 | p.76 の例外の対象外として切り捨て。警告と履歴を残す |
| 技能グループ付与、全段階 | XML の付与量を各構成技能へ加算 | 各技能で上限判定。所属技能なので移し替えプールは作らない |
| 知識・言語の数値付与、全段階 | 知識上限まで加算 | 再配分しない。知識超過は既存同様に作成エラー。切り捨てを原典の確定事項として追加しない |
| 母語の付与 | 現行の母語処理 | 数値0を未習得・超過ポイントと扱わない |
| 手動カルマ購入 | 付与後に加算 | 超過した購入はエラー。移し替えポイントは生成しない |
| キャリアでの成長 | キャリア上限まで購入 | 作成時の移し替えを再生成しない |

技能グループ所属は固定カタログの `skillgroup` で判定する。
購入済みグループの有無、現在グループが崩れているか、関連能力値の一致だけでは判定しない。
例えば First Aid は Biotech 所属なので、単独の `skilllevel` 付与でも移し替え元にはしない。

### 3.2 移し替え先の条件

同じカタログ上の関連能力値を持つ、別のアクティブ技能を対象にする。
関連能力値変更のダイス補正やサイバーリムの能力値は候補判定に使わない。
移し替え先に技能グループ所属があってもよい。グループ全体ではなく、その技能だけを上げる。
知識技能、言語、専門化、技能グループ全体、元技能自身へは移せない。
受け手の追加レベルが上限を超える指定は拒否し、新しい移し替えプールへ連鎖させない。

未習得技能への配分を許可する。Exotic は技能IDと具体名を指定して許可する (§4.2)。
ただし技能を習得できる条件を満たすこと。MAG / RES 関連技能はキャラクターの適性を
既存の talent 解決経路で判定する。無効化された技能への配分は拒否する。
`default=False` は「未習得で判定できない」であり、習得禁止条件として扱わない。
ルールブック選択は既存と同様に候補の表示フィルターとし、選択済み配分を黙って無効化しない。

### 3.3 原典からの推論・未確定点を実装規約へ落とす

| 決定 | 本設計の既定動作 | 根拠の区分・変更時の影響 |
| --- | --- | --- |
| p.66 と p.76 の関係 | p.76 を実生活・グループ非所属技能だけの特則とする | 採用解釈。反証があれば判定規約の版を上げる |
| Aptitude 等の上限修正 | モジュール付与・移し替えの上限は基準上限7。追加購入の上限には既存の技能上限修正を適用 | 採用解釈。標準ではモジュールで8は付与せず、適用可能な資質による手動購入8は別判定。厳密な原典準拠の公称前に要照合 |
| グループ付与量が2以上 | XML の val を各技能に加算。p.66 の1レベルの説明を理由に val を1へ変えない | データに基づく実装規約 |
| 移し替えの時点 | 各モジュールの直接付与を全部適用した後、次のモジュールへ進む前 | 採用解釈。イベント順と保存結果に影響 |
| 行き先を後続モジュールも上げる | 次のモジュールの付与として新たに上限判定する | 上記順序の帰結。移し替え時点で未来の全付与を先取りしない |
| 全候補が上限で配れない | 移せない残量のみ自動失効し、理由付き警告。配れる残量があるうちは未配分エラー | 採用する操作規約。意図的な配分放棄は不可 |
| 知識9超過 | エラーを維持。無償再配分や自動返金は行わない | 本文抽出では超過時の救済まで確定しないため |
| Further Education の回数 | PR #562 後の既存動作を維持し、この機能で変更しない | p.76 の「複数は実生活のみ」と現行の差異は別のルール課題として記録。準拠全般を公称しない |

上記は設計が未完了という意味ではなく、実装が従う既定仕様を明示したもの。
原典の照合で変更が必要になった場合は `policy_version` を変え、既存キャリアを
自動再計算で新解釈へ切り替えない (§11–12)。

## 4. 永続入力モデル

### 4.1 既存フィールドと経歴の安定ID

`life_modules: list[str]` と `life_module_choices: dict[str, str]` は互換性のため維持する。
追加選択の `選択位置:効果位置` キーを、移し替えキーとして流用しない。

新規フィールドを `CharacterState` / `CharacterPatch` と対応する TypeScript 型へ追加する。

```python
life_module_rules_version: Literal[1, 2] | None = None
life_module_entry_ids: list[UUID] = Field(default_factory=list)
life_module_transfers: list[LifeModuleTransfer] = Field(default_factory=list)
life_module_skill_snapshot: LifeModuleSkillSnapshot | None = None
life_module_skill_advancements: list[LifeModuleSkillAdvancement] = Field(default_factory=list)
```

- 新規 LifeModule 作成は `rules_version=2`。未指定の既存データは旧版として識別する。
- `entry_ids[i]` は `life_modules[i]` の取得イベントを表す。UUID は技能配分と独立して永続化する。
- 新規追加は新UUID。削除後に同じモジュールを再追加しても旧UUIDを再利用しない。
- 並び替えはモジュールと UUID を一緒に動かす。既存 choices の位置も同じ置換で変換する。
- v2 で個数不一致・UUID重複は入力エラー。正しい既存データから UUID を黙って再発行しない。
- 旧作成データの移行時だけ、`uuid5(namespace, character.id + index + module_id)` で決定的に採番する。
- 共有リンクの取り込みでキャラIDを変更しても、既存の entry UUID は維持する。

`apply_patch` は変更後の候補を組み立ててから整合性を検証する。
v2 の経歴追加・削除・並び替えは `life_modules`、`entry_ids`、`choices` を同じリクエストで更新する。
旧クライアントが v2 の経歴一覧だけを変更した場合は、推測で紐付けず構造エラーを返す。
移し替え入力は全リスト置換とし、操作順による差分マージ競合を避ける。

### 4.2 配分モデル

```python
class LifeModuleTransfer(BaseModel):
    id: UUID
    entry_id: UUID
    source_skill_id: str
    grant_fingerprint: str
    destination_skill_id: str
    destination_specific: str = ""  # Exotic の場合だけ必須
    ranks: Annotated[StrictInt, Field(ge=1, le=1000)]
```

プールキーは `(entry_id, source_skill_id)`。同じモジュールで同じ技能へ複数の付与が
あれば先にまとめ、プールは1個にする。XML内の効果位置を永続キーにしない。
`grant_fingerprint` は、元技能ID・付与量・人生段階・元の選択結果・関連能力値・
グループ所属・判定規約版から正規JSONを作り SHA-256 で計算する。
表示名・翻訳・説明・カタログの並びだけの変更では変わらない。
元の定義や選択の意味が変わった配分は保留して修復できるようにする。
ポイント量は保存しない。エンジンが毎回再計算する。

同一プール内で同じ移し替え先を複数行に分ける入力はエラーとし、UI は同じ行の数値を編集する。
Exotic の具体名は前後空白を除去し、既存 Exotic の同一性規約と合わせて大小文字差を正規化する。
通常技能には具体名を認めない。Exotic の空具体名・プレースホルダーは拒否する。
既存の購入行がなくても無償 Exotic の行は derived で生成し、入力の購入行を捏造しない。

構造上の防御上限は経歴512件・配分4096行・具体名200文字とする。
既存のリクエストサイズ・コレクション制限と両方を適用し、最も厳しい制限が有効。
超過量を1ポイントずつループせず、整数の差と min/max で計算する。
未知の技能ID・指紋不一致など意味上の不正は、構造上正しい配分行を残して作成エラーにする。

### 4.3 ルールコンテキスト

作成中は以下を毎回解決し、キャリア開始時にスナップショットへ固定する。

```text
policy_version
module_active_cap      # 設定が未指定なら7、技能ごとの資質修正を含めない
knowledge_cap          # 設定が未指定なら9
purchase_cap_by_skill  # 基準上限 + 適用できる資質等の上限修正
dataset_fingerprint    # 実際に参照したモジュール・技能の計算関連定義
```

`rules_for()` は全作成方式へ共通なので、LifeModule の未指定時既定値は
`resolve_life_skill_policy(state, data)` で解決する。`DEFAULT_RULES` を7/9に変更しない。
キャリア時も「モジュール付与の上限」はキャリア上限12へ置き換えない。

## 5. derived の契約

`derived.life_module_skills` を新設する。フロントエンドはこの結果を表示し、
超過量・候補・課金を独自に再実装しない。

```text
version: 2
policy: { version, active_cap, knowledge_cap, caps_overridden }
free_active: { skill_key: ranks }
free_knowledge: { name: ranks }
groups: [{ name, member_keys, member_free_ratings, uniform, free_uniform_rating }]
pools: [{
  key, entry_id, source_skill_id, source_name, stage,
  before, grant, kept, total, allocated, remaining, unallocatable,
  grant_fingerprint, status,
  candidates: [{ skill_id, specific_required, attribute, capacity, unavailable_reason }],
  transfers: [{ id, requested, applied, status, error_key }]
}]
losses: [{ entry_id, skill_key, before, grant, kept, lost, reason }]
purchase_preview: { groups, active, knowledge, karma }
complete: bool
frozen: bool
legacy: bool
```

`skill_key` は通常 `skill:<catalog-id>`、Exotic は `exotic:<catalog-id>:<normalized-specific>`。
既存の名前キーを使う `derived.skill_totals` への変換はアダプターが担当する。
`free_uniform_rating` は全構成技能が一致するときだけ数値、不一致なら null。
最小値を「無償グループレベル」と誤認しない。
プールの候補 capacity は、そのプールへ割り当てる直前の状態に対する最大値。
既存の同プール配分を外した状態の値を返し、編集で空きが二重に減らないようにする。
`complete=false` でも入力と計算可能なプレビューは返すが、キャリア確定は許可しない。

## 6. 計算アルゴリズム

### 6.1 モジュールの検証と順序

1. 現行と同じ未知ID・未対応効果・前提・段階重複・親ID重複の検査を行う。
2. 不採用モジュールは技能付与と費用へ加算せず、その取得に紐付く配分は孤立入力として表示する。
3. 有効なモジュールを `(STAGES の順序, 保存一覧内の位置)` で安定ソートする。
4. 保存一覧・choices の位置を実際に並び替えず、計算用の列だけを作る。
5. 同じ段階内の順序変更は結果へ影響し得るため、UI で明示的に並び替え可能にする。

過去に実生活を先に追加してから国籍を追加したデータでも、国籍を先に計算する。
追加選択に不足がある技能付与はその効果だけ未解決として扱い、プールを推測で生成しない。
他の確定効果はプレビューへ出すが、未解決状態でキャリア確定はできない。

### 6.2 直接付与

購入入力は使わず、モジュール由来の無償レベル `F[skill_key]` を0から構築する。
モジュール内の直接技能付与とグループ展開分を技能ごとにまとめる。
技能グループの量は、その時点の各構成技能へ同じだけ加える。
複数のグループ付与と単独付与を二重加算しないよう、展開は1回だけ行う。

各元技能について以下を計算する。

```text
before = F[s]
grant  = 当該モジュールの s への合計付与量
kept   = min(grant, max(0, module_active_cap - before))
excess = grant - kept
F[s]  += kept
```

`excess > 0` かつ §3.1 の対象ならプールを生成し、それ以外は loss 行を生成する。
知識は別の集計経路とし、超過時に error を記録する。無償上限超過を通常の手動購入へ変換しない。
母語、資質、能力値、コンタクトなどの処理は現行経路を使う。

### 6.3 モジュール内の配分

1. 当該モジュールの全直接付与を終える。
2. 生成プールを元技能のカタログIDの昇順で処理する。この順は表示にも明記する。
3. 現在の `F` に対して候補と capacity を計算する。異なるプールは先行する配分を反映する。
4. プールに紐付く入力を集合として検証する。行順で先着勝ちにしない。
5. 未知の行き先・条件不一致・重複行・過配分・容量超過・指紋不一致があれば、
   当該プールの配分は全行適用しない。直接付与の kept は維持し、入力は残す。
6. 有効な配分を `F[destination] += ranks` で適用する。移し替えは別の超過を生成しない。
7. 残量があり、受け手に空きがあるなら pending エラー。受け手すべての容量が0なら、
   配れない残量だけを unallocatable として失効し警告する。
8. 次のモジュールへ進む。後続の直接付与は、先行する移し替え後の F を基準に判定する。

候補が有限でない Exotic については、有効な具体名の新規習得が可能なら
「候補がない」とは判定しない。新規具体名は同じ関連能力値の条件を満たす必要がある。
無限列挙はせず、Exotic の技能IDごとに具体名入力を提示する。

先行プールが不正・未配分なら、後続は現在適用済みの値で暫定計算し `complete=false` を引き継ぐ。
後続の未配分量が確定値でないことを UI に表示する。
配分した技能が後続モジュールで上限へ達することは、その後続イベントの超過として処理する。
手動購入は全モジュール・配分の後なので、購入を増やして配分原資を作れない。

### 6.4 保存と再計算の不変条件

```text
直接付与量 = kept + transferable_excess + lost
各プールの total = allocated + remaining + unallocatable
0 <= F[s] <= module_active_cap
配分から増えた受け手のレベル総数 = 適用した配分量総数
compute(compute(state)) == compute(state)
```

モジュール削除時には原資も受け手への付与も消える。
`ctx.state` の作業用コピーだけへ無償付与を適用し、返却する `skills` / `skill_groups` /
`knowledge_skills` / `exotic_skills` は購入入力に戻す。`FIELDS` の Exotic 対応漏れを防ぐ。
入力正規化によるバージョン・UUID追加は永続化対象とし、復元処理で消さない。

## 7. 計算フェーズへの接続

現状の `_life_modules.prepare()` は無償レベルを一括加算しており、
技能グループの表示値と構成技能の付与値を同時に保持する。
v2 は技能処理を独立させて、元の購入入力を上書きする前に解決する。

```text
bootstrap
  -> normalize_life_module_inputs / resolve_life_skill_policy
  -> life.prepare（選択検証、能力値・資質等の既存付与、技能イベント収集）
  -> gather / ware / effects_and_binders / essence / awakened
  -> life.resolve_skills（適性・無効化を反映して §6 を計算）
  -> gear / totals / spells
  -> economy._skill_spend（v2 の無償ベクトル + 購入を解決）
  -> economy._karma_totals（v2専用価格）
  -> finalize / assemble / restore
```

新設候補: `engine/life_module_skills.py`（純粋計算）、
`engine/compute/_life_module_skills.py`（Ctx 接続）、`models/life_modules.py`（入力・スナップショット）。
純粋計算は `state.derived` を参照せず、必要なカタログ・入力・解決済み適性を引数で受ける。
技能ダイス補正は従来どおり最終計算へ適用し、レベル移し替えの量へ加えない。
技能の上限修正は既存 `resolve_skill_picks` の上限修正解決を共通化し、
技能計算をもう一度呼んで整合させる循環依存を作らない。
通常技能の内部 clamp が検証前に8以上を消してしまわないよう、v2 は要求値を先に検証する。

`_econ_skills._skill_spend` のv2接続は、元の購入入力とFから `resolve_life_purchases` を
呼び、解決済み技能値・有効なグループ購入・価格用範囲を受け取る。
現行のグループ展開ループへ「無償グループレベル」を流し込んで再度加算しない。
既存の `_check_grouped_skills` は非v2経路に残し、v2では §8.2 の判定を使う。
技能補正・ダイス・専門化・skillsoftの処理は、解決済みの技能値を引数に既存経路を共有する。
旧 `life.price()` の技能/グループ価格・上限検査をv2価格と重ねて実行しない。
知識・能力値・資質・専門化の価格はそれぞれの担当処理へ接続する。

## 8. 手動購入とカルマ

### 8.1 入力の意味を維持する

`skills[s] = P[s]` と `skill_groups[g] = G[g]` は引き続き手動購入側の値。
現行の「単独購入入力とグループ購入入力の大きい方を使う」意味を維持する。

```text
無償値 F[s] = モジュール直接付与 + 移し替えの受取
購入後 B[s] = F[s] + max(P[s], G[group(s)])
単独で購入する追加レベル = max(0, P[s] - G[group(s)])
```

グループ非所属なら G=0。Exotic は `F[exotic-key] + P[exotic-key]`。
入力値を勝手に減らして上限へ収めない。`B[s] > purchase_cap[s]` は作成エラー。
プレビューは合法な上限値と要求値の両方を出し、不正入力を保存・修復できるようにする。

### 8.2 技能グループ購入

モジュールのグループ付与は全構成技能への加算として処理するため、
不揃いの技能群を最小値で一つの無料グループとみなして購入価格を計算しない。

- 全構成技能の F が同じ `b` の場合、G レベルのグループ購入を `b -> b+G` として課金する。
- F が不揃いなら、新規のグループ購入を不可とし、個別技能購入へ誘導する。
- 旧データに不揃いのまま G>0 があれば入力を残して作成エラー。個別購入へ変換する操作を提供する。
- 変換は各構成技能の P を `max(P, G)` へ更新して G を0にする。技能値は維持するが、費用は再計算し差を表示する。
- 構成技能の1つでも手動購入・専門化等でグループ購入不可になる条件は、既存グループ制約も検査する。
- 移し替えが構成技能の1つだけを上げた場合も F の不揃いとして扱う。

### 8.3 課金式と修正値

単独技能は `F[s]+G -> F[s]+max(P,G)`、グループは `b -> b+G` の範囲を課金する。
既存の `skill_levels_karma_cost`、カテゴリ別倍率・カルマ補正・新規技能費用を使用する。
v2 で無償付与を価格の対象範囲へ含めない。無料グループを `state.skill_groups` に
足してから旧価格式で差し引く方法は使わない。
`group_karma_compensation` を使う場合も、有償追加レベルだけを対象とし、
移し替え・直接付与に返金を発生させない。既存式へ F を含む総値を渡さない。

知識は既存の無料知識ポイントと無償モジュールレベルを分ける。
移し替えは知識ポイント枠を使わない。母語には数値購入費を発生させない。

標準費用の数値例:

| 無償状態と購入 | 最終値 | 追加カルマ |
| --- | --- | --- |
| 移し替えを含む F=5、P=1、G=0 | 6 | 6×2=12 |
| F=0、P=1、G=0 | 1 | 新規技能の設定値（標準2） |
| 全構成技能 F=2、G=1、P=0 | 各3 | 3×5=15 |
| 全構成技能 F=2、G=1、ある技能のP=2 | その技能4、他3 | グループ15 + 単独4×2=8、計23 |
| F=7、P=1、通常の作成上限7 | 要求8 | エラー。超過1を配分原資にしない |

能力値などの価格は現行の担当処理を維持する。v2 の技能価格だけを置き換える。

## 9. 編集とエラー

| 操作・入力 | エンジンの動作 |
| --- | --- |
| 元モジュールを削除 | その entry の配分行を同じ patch で削除。別 entry は維持 |
| 元の技能選択を変更 | プールを再計算。指紋不一致の行は未適用で保持し、削除または新候補への修復を案内 |
| 前段のモジュールを削除 | 超過量を再計算。原資より配分が多ければそのプールを未適用にする |

| 同じモジュールを削除後再追加 | 新UUID。旧配分を自動復活させない |
| 同段階で順序変更 | UUIDとchoicesを維持し再計算。配分量・候補の変化を表示 |
| 不明な経歴・重複・前提不成立 | 現行のエラー + 関連配分を未適用 |
| 行き先変更・上限変更 | プール全体の容量を再検証 |
| 書籍を表示フィルターから外す | 選択済み行は表示・計算を維持 |
| 作成方式を他方式へ変更 | 配分入力は休眠保持。付与は適用しない。LifeModuleへ戻れば再検証 |
| 構造エラー | API 422（既存入力検証経路） |
| 意味上の不正・未配分 | 200 + structured notice、入力保持、キャリア確定不可 |

日本語・英語を追加し、通知から人生経歴/技能の該当タブへ移動できるようにする。
`ratingCap` の「すべての超過精算が未対応」という既存文言は、能力値・知識・資質の
残る未対応と技能の対応範囲を区別する文言へ改める。

## 10. UI

### 10.1 人生経歴タブ

各経歴カードの追加選択の下に「技能の超過分」を表示する。検索でカード・配分欄を隠さない。
グループ名や元技能が同名でも entry UUID をキーにして表示状態を分ける。

```text
技能の超過分
知覚（直観力）: 6 + 2 → 7、移し替え可能 1
  移し替え先 [候補から選択]  レベル [1]  [削除]
  残り 0 / 1
```

- 候補には現在値と追加可能量を示す。容量0や適性不成立のものは理由付きで追加不可。
- 行追加・数値変更はドラフトを保持し、確定時に配分リスト全体を patch する。
- 同一画面内の経歴・配分変更は既存の更新キューに直列化する。送信中の同じ操作を無効化し、
  古い応答で新しいドラフトを上書きしない。処理エラーならドラフトを保持して再送できる。
- Exotic は具体名入力を伴う。空具体名のまま確定しない。
- プールの処理順を「この経歴内での適用順」として表示し、表示名ソートで順序を変えない。
- 切り捨ては配分欄とは別に「上限により付与されないレベル」と理由を表示する。
- 過配分・孤立行・定義変更は入力内容を見せ、利用者が削除・修復できる。
- 同段階の順序変更ボタンを追加する。人生段階を越えるドラッグは提供しない。
- career では経歴・choices・移し替え・順序を読み取り専用にする。

### 10.2 技能タブ・作成チェック

技能行は「経歴の無償付与 F / 手動購入 / 合計 / 上限 / 追加カルマ」を区別する。
手動入力の上限は `purchase_cap - F` を基準にし、グループ側の購入も考慮する。
不正な既存入力はスライダーで消さず、要求値を表示して修復できるようにする。
グループ行は不揃いの場合に構成技能の値と購入できない理由を表示する。

作成チェックは未配分・不正配分・不正購入をエラーにし、該当カードへ移動できるようにする。
切り捨て警告と、全候補に空きがないための失効警告はキャリア確定を妨げない。
原典の採用解釈は短い説明からヘルプへ辿れるようにする。内部キーや指紋は通常画面へ出さない。
キーボード操作、入力のラベル、フォーカス維持、処理中の二重送信防止を既存 UI に合わせる。

## 11. キャリア移行

### 11.1 上限変更による復活を防ぐ

作成時の切り捨て・移し替えは、キャリア上限12で再計算しない。
`LifeModuleSkillSnapshot` に作成時に確定した結果を保存する。

```text
version / policy_version
creation_policy（作成時上限、購入上限修正）
entry_ids / module_ids / choices_fingerprint / transfers_fingerprint
dataset_fingerprint
free_active / free_knowledge / native_languages
losses / applied_transfers
purchased_active_inputs / purchased_group_inputs / purchased_exotic_inputs
purchased_knowledge_inputs / knowledge_categories
resolved_creation_active / resolved_creation_knowledge
skill_metadata（参照技能のID・表示名・関連能力値・グループ・Exotic具体名）
creation_skill_karma / creation_knowledge_karma
creation_group_karma / creation_knowledge_point_allowance
```

1. `career=true` を含む patch の全更新をまず適用する。
2. 候補を `career=false` として v2 計算する。同時更新された配分や技能購入を含める。
3. 全作成エラーが解消し、配分 `complete=true` であることを検証する。
4. その候補の計算結果からスナップショットを作り、初めて career を true にする。
5. 現状の `snapshot_career_baseline(state)` を patch 前の state に対して呼ぶ経路を、
   LifeModule v2 については置き換える。他方式の移行処理はこの変更で変えない。

これは同時 patch の取りこぼしと、無償付与を含まない購入入力だけの snapshot を避けるため。

### 11.2 キャリア中の計算と制約

- 無償レベルはスナップショットから読み、作成時のプールを再生成しない。
- 作成時の技能購入カルマは固定し、開始時の解決済み値から成長イベントを順に適用する。
- 追加技能購入は開始時の解決済み値から課金する。7→8は標準16 Karma。
- グループ成長は全構成技能の現在値が一致し、既存のグループ成長条件を満たす場合だけ許可する。
- 個別成長でグループが崩れた後の成長も、現在値から課金し、作成時の無償分へ戻さない。
- 属性成長で無料知識ポイントが増えても、作成時の知識購入代を遡って返金しない。
- 経歴・choices・移し替え・作成方式・作成技能上限の変更は API 側でも拒否する。
- v2キャリアでは、作成時の `skills` / `skill_groups` / `exotic_skills` /
  `knowledge_skills` の購入入力を固定し、成長は下記の専用イベントへ記録する。
- 将来取得する Aptitude 等の資質はキャリア購入上限へ反映してよいが、無償付与を増やさない。
- customdata/カタログの変更で定義が変わった場合も固定値を維持する。参照先技能自体が不明なら
  IDと旧表示名を保持して互換性エラーを表示し、別技能へ近似しない。
- `career=false` へ戻す場合はスナップショットを解除して元の入力から再計算する。
  成長イベントの最終値を、無償Fを除いた購入入力へ変換して保持し、成長イベントは休眠保存する。
  不揃いグループの成長分は個別Pへ展開し、無効な無料グループを作らない。
  作成上限超過ならエラーになる。黙って成長を削除しない。

キャリアで frozen 入力とスナップショットの指紋が一致しない state は、
整合性エラーを返して保存内容を保持する。stateless API の入力を信頼して配分原資を増やさない。
指紋は改ざん防止署名ではなく整合性照合用である。必要な数値範囲・非負・参照の検証も行う。

### 11.3 キャリア成長イベント

作成時の `F + max(P,G)` をそのままキャリアの価格差分へ使うと、個別購入で既に上がった
技能群のグループ購入が値を上げなかったり、重複課金を起こしたりする。
そのためv2キャリアの技能成長は、既存 `CareerBaseline` の raw P/G の差だけでは計算しない。

```text
LifeModuleSkillAdvancement:
  id: UUID
  kind: active | exotic | group | knowledge
  target_id: 技能IDまたはグループ名
  specific: Exotic具体名、それ以外は空
  levels: strict positive integer
  from_ratings: { skill_key: int }  # 記録時点の開始値
  rule_context: その成長に使う価格設定・適用補正・上限
```

`CharacterPatch` のコレクション置換として成長リストを受け取り、保存前に先頭から検証する。
記録された `from_ratings` と直前イベントまでの解決値が一致することを必須にする。
API はイベント入力から価格を再計算し、クライアントの任意のcost値は受け取らない。
`rule_context` は当該 patch 時にサーバーが解決して生成し、履歴の価格を後日の設定変更で再課金しない。
stateless の import/compute でも同じ算術検証を行う。真正性を保証する署名付き台帳とはしない。

- 単独成長は現在技能値 r から r+n へ加算し、各到達レベルの費用を合計する。
- グループ成長は対象全員が同じ r の場合だけ、全員を r+n にし、グループ費用を1回課金する。
- 配分で上がった技能も現在値に含める。既存P/Gの上書きで値を巻き戻さない。
- 知識成長は開始時9等からキャリア知識上限まで通常費用で購入し、新しい無料知識ポイントを使わない。
- 成長イベント後の最終値を技能タブ・シート・全エクスポートへ同じように渡す。
- 技能タブのキャリア操作は、raw P/G編集ではなく成長イベント追加へ接続する。
- 取り消しは末尾イベントから可能にする。中間の削除・編集は後続の開始値不一致をエラーとして
  表示し、後続のイベントを自動で別価格へ書き換えない。
- 作成へ戻してから再びキャリアを確定するときは、旧成長ログは履歴のみとし、新snapshotを基準に
  activeな成長ログを空にする。同じ成長を二重適用しない。

標準の例: 作成完了時、あるグループの3技能が全て4（無償2、グループ購入1、個別入力2）なら、
グループ成長+1で全員5、費用25 Karma。作成時Gを1→2に変えて全員4のままにする処理は不可。
キャリア技能費用は `固定した作成時技能費用 + 有効な成長イベント費用の合計` とする。
`_econ_karma` の他の支出と合算するとき、旧v2技能再価格を重ねて加算しない。

## 12. 既存データ・保存・共有

| 入力 | 動作 |
| --- | --- |
| 新規 LifeModule | v2、標準7/9、空の配分、取得時UUID |
| v1/版未指定、作成中 | v2へ移行して UUID を採番し、空の配分から再計算。購入入力とchoicesは維持 |
| 移行により超過プール発生 | 未配分として表示。受け手を自動選択しない |
| 設定に6等が明示済み | その値を維持。標準7/9を強制しない |
| v1/版未指定、キャリア中 | v1互換計算を維持し「旧方式」と表示。開始時の配分結果は推定しない |
| v2キャリア、snapshotなし | 不正データとして明示エラー。現在値から無断復元しない |
| 将来の未対応版 | 明示エラー。v1/v2として黙って読むことをしない |

旧キャリアのv2移行は、作成状態へ戻して経歴・購入・配分を解決し直し、再確定する明示操作とする。
過去の作成値が確定できないまま現技能値から無償付与を逆算しない。

バックエンドが移行の唯一の計算主体。IndexedDB の record schema は必要な版へ上げるが、
ブラウザ側でルールを再計算しない。読込後に API の正規化結果を保存する。
JSON バックアップは新フィールドを全て保存し、derived は再計算する。
共有リンクでは新フィールド・スナップショットを除外リストで落とさない。
共有形式は `SHARE_VERSION=2`、IndexedDBレコードは `SCHEMA_VERSION=2` とし、
新コードは各v1も受け付ける。DBのobject store構造は変わらないため、DB自体の版上げは不要。
旧コードへの前方互換は保証せず明示する。
UUIDは共有でキャラIDを再発行しても保持する。
エクスポートの処理途中で入力へ free 値を焼き戻さない。

## 13. chum5 入出力

現状は `_export_skills` が購入入力を出力し、`lifemodulechoices` が本アプリ再構築の情報を運ぶ。
無償付与を含む最終値を出す投影と、購入入力を復元する情報の両方を設計する必要がある。
既存ドキュメントの「Chummer向けに付与を焼き込む」という説明だけで互換性完了としない。

### 13.1 出力

- Chummer標準の `<newskills>` には解決済みの技能・知識値を出す。
- 不揃いのモジュール由来技能を、偽のグループ値へまとめて出さない。
- 本アプリ専用 `<lifemoduleskillstate version="2">` に、判定規約、entry UUID、
  choices、配分、購入入力、キャリアsnapshot、成長イベントを保存する。
- XML は型ごとの要素として構造化し、任意のPython式・eval可能な文字列を入れない。
- v2では旧 `<lifemodulechoices>` マーカーを出さない。旧アプリはこれがない LifeModule の
  読み込みを拒否するため、標準欄の解決値を購入値として二重加算する事故を防げる。
  新アプリの `life_module_choices_present` は旧マーカーまたはv2専用要素を判定する。
- 標準技能値へ焼いたモジュール付与を `SkillLevel` improvement として重ねて出さない。
- 能力値・資質など既存付与の投影との一貫性も確認し、skillsだけの往復成功を全体互換と呼ばない。

### 13.2 入力

- v2専用要素があれば、その購入入力・配分を検証して正規の state を組み立て、再計算する。
- 標準技能欄の最終値をそのまま購入入力にして再付与しない。
- 再計算した値と標準欄が食い違えば、Chummerで編集された可能性として互換性エラー。
  専用要素だけを信じて編集を捨てたり、差分を推測で購入へ変換したりしない。
- 旧専用要素のみなら §12 のv1移行を適用する。
- 旧マーカーとv2要素が両方あるファイルは、競合する二重状態として拒否する。
- Chummer本体だけが保存した LifeModule は、choicesを逆算できない現状の拒否を維持する。
- 将来版・壊れたentry対応・重複UUID・不明skill ID・不足snapshotは明示エラー。

Chummer本体で開く試験では、LifeModule quality の再ロード時に付与が再適用されないこと、
標準技能の保持、キャリア上限、保存し直した後の扱いを確認する。
標準欄を焼くだけで全動作が保証されるとは仮定しない。ここは純粋な本アプリ往復試験と別の互換性判定。

## 16. 実装順とリリース条件

1. 原典の照合記録・§3の採用規約を確定し、7/9・設定優先・Aptitudeの境界試験を作る。
2. 入力モデル・UUID正規化・v1/v2識別を追加する。既存JSONの往復を先に確保する。
3. 純粋なイベント計算・配分検証・保存則を実装する。
4. 購入・技能グループ・Exotic・価格を接続し、既存方式の回帰試験を実行する。
5. 配分UI・並び替え・不正入力修復・作成チェックを接続する。
6. キャリア確定・スナップショット・成長課金を実装する。
7. JSON/共有/chum5互換と移行を実装し、Chummer本体で開く試験を行う。
8. 日英説明・現行ドキュメント・changelogを更新する。

この設計を実装し、技能移し替え・購入・キャリア成長をv2状態へ接続した。上限だけを有効にして
移し替えを後回しにする状態にはしない。既存キャリアを別結果へ自動移行しない。
リリース条件は FR-01〜15 の試験通過、代表的な既存作成方式の回帰検証、
永続化とキャリアの固定点、原典の採用解釈の明記である。
Chummer本体との操作互換性を確認できなければ、その部分を未検証と明記し、
本アプリの往復成功だけで「Chummerとの互換性確認済み」と表示しない。
