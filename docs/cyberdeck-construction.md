# デッキのプログラム・モジュール・電子改造

2026-10-09実装。実行プログラム数、物理モジュール数、施工に使う電子部品は別々に管理する。

## 操作と互換性

デッキのプログラムは搭載数に制限を掛けず、新規購入と予備からの搭載は停止状態にする。「作動中」で切り替え、作動中だけを同時実行上限と比較する。超過は警告し、保存や切り替えは拒否しない。停止しても購入費と搭載先を保持する。旧JSONのrunning欠落はTrueとして読み、RCCの既存集計にはrunningを使わない。

通常のデッキは物理モジュール1枠を持つ。Deck Builderは対象デッキ1台の通常枠を1つ増やす。複数デッキ所持時は対象を選択し、1台のみなら自動的にそのデッキを対象とする。有効なAdd Module改造には独立した直結1枠がある。通常側の超過を直結側の空きで相殺しない。

モジュールは数量を含めて数え、無効化しても枠を占有する。「取り外す」は所有を残し、「削除」は購入行を削除する。数量付き予備から搭載する操作では1個を別行へ分割する。超過・不正配置でも所有行は残す。超過したプールの効果を全て無効とし、別プールへ波及させない。CoprocessorのVRイニシアティブ効果は搭載機器に限定し、ペルソナ選択後に適用する。同種効果は重複加算しない。

Program Carrier等の選択値と装備指定は保持する。Coprocessor以外の個別モジュール効果の新実装は含まない。「個別効果は手動確認」の表示を参照する。過去に予備モジュールから得ていた全体ボーナスは、搭載条件を満たすまで適用されなくなる。

## 電子改造の材料

Data Trails pp.64–66を基準とし、名前の翻訳ではなくカタログIDで規則を指定する。

| 改造 | 必要部品 | 条件 |
| --- | --- | --- |
| Increase Matrix Attribute | 上昇後の値×2パック | 対象能力が既にある。Matrix状態モニターに永続ダメージ2 |
| Modify Matrix Attribute | 4パック | 配列型は配列を持つ機器。変更後の値が負にならない |
| Add Attack / Sleaze | DR×2パック | 対象能力がなく、配列型デッキではない |
| Add Module | 2パック | 通常の電子改造数制限と材料確認を満たす |
| Persona Firmware | 2パックという原典規則あり | 現在のデッキ・RCC・コムリンクはペルソナを持つため追加不可 |

通常の電子改造は機器ごとに1件。Add Attack / Sleaze配下の対応するIncreaseのみ例外として扱い、1→2なので4パック必要。未知のCustom改造・Decrease単独・未対応の特殊機器へ規則を推測して適用しない。

必要数の基準は施工前の機器本体のASDF・DRと配列順。Overclockerや外付けドングルを施工対象の恒久能力として数えない。完成時にこの値と必要数を保存し、後の配列変更や再計算では追加消費や返金をしない。成功した施工を利用者が登録する方式で、技能判定・失敗・グリッチの材料損失は自動処理しない。

改造追加は「準備中」で保存され、効果はまだない。配分を保存すると部品を予約し、他の施工へ重複配分できなくなる。必要数に一致する配分を確認し「施工済みにする」と消費と効果を確定する。不足分の購入は利用者が単品／5パック・数量を選ぶ。自動購入はしない。

旧JSON・外部取り込みの材料記録がない改造は「履歴未確認」とし、既存互換の効果を維持する。現在の材料を配分して施工記録を補うか、説明を付けて過去の調達済み履歴を登録できる。通常PATCHで新しく追加した改造は自動的に準備中とし、旧履歴に分類しない。

## 在庫と支出

`gear.qty`は購入した販売単位数。単品はqty=1で1パック・250¥、5パック商品はqty=1で5パック・1,000¥。材料は1/4パックを1とする整数で保存する。

- `electronic_parts_supplies`：回収・設備付属・GM指定の明示的な調達記録。
- `electronic_modification_records`：対象機器・改造行・状態・必要数・施工前能力・配分・理由を保持する施工履歴。
- 在庫残量＝購入・調達量−施工済み使用量。利用可能量はさらに準備中予約を引く。
- 購入行のqtyを消費によって変えない。派生所持数量・シート・外部出力には残量を使う。

5パック商品から4パック消費すると、残量1パック、購入費1,000¥が残る。割引・親数量倍率も購入時の構造を保持する。使用済み購入行と、その数量・価格に影響する親行は通常編集・削除から保護する。完成した改造や機器の削除では使用履歴を残し、部品を返さない。

誤入力の訂正は理由付き「記録取消」で行う。取消後は効果を無効化し配分を解放するが、部品の購入記録は残す。履歴自体の消去や完成時必要数の書き換えを拒否する。移設は新しい施工が必要。

Hardware Shopの2パック、Facilityの10パックは明示登録する。同じ設備の重複登録と付与済み記録の数量変更を拒否し、所持しているだけで自動補充しない。設備の削除でも登録済み部品・使用履歴は残る。

## 保存・外部形式

JSON保存・IndexedDB・共有リンクが全履歴の復元基準。再計算は在庫・資金・履歴を追加変更しない。APIはキャラクター全体を受け取る既存のステートレス方式であり、サーバーに過去履歴を保管する台帳ではない。

| 形式 | 対応 | 制約 |
| --- | --- | --- |
| JSON・ローカル保存・共有 | 作動／装備指定、親子構造、購入・調達・施工履歴を保持 | 完全なバックアップに使用する |
| .chum5 | equipped、通常／直結モジュールの構造、部品残量・1/4パック数量、完成した改造を出力 | Web独自の施工履歴は復元できず、取り込み後の改造は履歴未確認 |
| .chum5の資金 | 成長後の残金は既存の資金取り込み処理で保持 | 作成中に消費した部品の過去支出は残量の標準装備行だけで復元できない。出力前の差分表示で資金変化を確認する |
| Foundry | 作動／装備指定、部品残量、完成した改造を出力 | 平坦な入力では搭載先を推測しない。再設定が必要。Web施工履歴を保持しない |
| XLSX | 整数パックの残量、完成した改造を所持品へ出力 | 小数数量の部品は警告して省略。搭載先・施工履歴の完全復元はできない |

準備中改造とその子装備、残量0の部品を外部所持品として出力しない。無料調達分は費用0の残量として出力する。部品が親数量を持つ容器内にある場合、.chum5では総残量を上位へ出し、数量の再乗算を防ぐ。

`.chum5`はアプリ内往復テストで確認した。Chummer.exeで開いて再保存する確認は未実施。この環境にはWine/.NET実行環境がなく、Windowsでの確認が残る。独自XMLタグによる完全保存は採用していない。
